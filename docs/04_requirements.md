# Формализация требований

## User Stories

### US-01. Приватная оценка без участия HR и руководителя

Как участник команды,
я хочу приватно оценить состояние команды по 8 параметрам и выбирать теги проблем,
чтобы высказаться честно, не опасаясь, что мой ответ увидят руководитель или HR

Критерии приемки:

```gherkin
Given участник команды получил одноразовый токен участия
 When участник команды открывает форму оценки
 Then он видит 8 параметров со светофором и справочник тегов
  And форма не запрашивает ФИО, email, грейд и стаж

Given участник команды заполнил оценки
 When он отправляет форму
 Then запись сохраняется в зашифрованном виде с TTL 24 часа
  And в записи нет постоянного идентификатора участника команды

Given участник команды хочет выйти из сессии
 When он нажимает «Выйти без сохранения»
 Then его ответы не сохраняются
  And никаких санкций не применяется

Given участник команды уже использовал токен
 When он пытается открыть форму повторно
 Then система отклоняет повторный вход по тому же токену
```

### US-02. Командная сессия с нейтральным фасилитатором

Как член команды,
я хочу увидеть агрегированные оценки и обсудить разногласия без HR и/или руководителя,
чтобы понять реальное состояние команды и решить, что мы можем исправить сами

Критерии приемки:

```gherkin
Given в команде ответили не менее 5 человек
 When команда открывает командную доску
 Then она видит распределение оценок по 8 параметрам
  And система не позволяет открыть индивидуальную строку

Given на доске есть расхождения по параметру
 When фасилитатор открывает карточку
 Then он видит только агрегат («3 зеленых, 2 желтых, 1 красный»)
  And не видит, кто как голосовал

Given команда решила, что проблему можно решить локально
 When она фиксирует локальный план
 Then создается запись с владельцем и сроком
  And проблема не передается за пределы команды

Given в команде ответили менее 5 человек
 When команда открывает доску
 Then командный срез не публикуется
  And система предлагает когортный отчет или офлайн-сессию
```

### US-03. Командное согласование проблемы

Как команда,
я хочу одобрить формулировку проблемы перед передачей,
чтобы наружу ушло только то, с чем мы все согласны, и ничего лишнего

Критерии приемки:

```gherkin
Given команда сформулировала текст проблемы
 When фасилитатор запускает голосование
 Then каждый участник голосует анонимно «За» или «Против»
  And система показывает только кворум и долю поддержки

Given кворум ≥ 70% и поддержка ≥ 60%
 When голосование завершено
 Then проблема помечается как «Одобрена командой»
  And уходит на проверку компонента «Защита конфиденциальности»

Given кворум < 70% или поддержка < 60%
 When голосование завершено
 Then проблема не передается
  And фиксируется в consent_log как «Не одобрена»
  And команда может переформулировать проблему
```

### US-04. Проверка риска идентификации

Как специалист по приватности,
я хочу проверить проблему на риск идентификации автора перед публикацией,
чтобы команда не пострадала от раскрытия, а доверие к процессу не упало

Критерии приемки:

```gherkin
Given проблема одобрена командой
 When специалист по приватности проверяет текст
 Then он ищет ФИО, контакты, редкие роли, названия малых команд и уникальные детали
  And блокирует публикацию при обнаружении риска

Given специалист по приватности нашел риск
 When специалист по приватности открывает проблему
 Then он может запретить публикацию или вернуть на правку
  And обязан указать причину

Given специалист по приватности не ответил за 2 рабочих дня
 When срок истекает
 Then эскалация уходит к специалисту по приватности уровнем выше
  And проблема остается блокированной
```

### US-05. Предложение обобщенного наименования кластера внешней моделью

Как HR-аналитик,
я хочу подтвердить, изменить или отклонить предложенное внешней моделью наименование кластера,
чтобы смысл проблем и приоритет определял человек, а не модель

Критерии приемки:

```gherkin
Given внешняя модель предложила кластер по ≥ 3 обезличенным проблемам
 When HR-аналитик открывает предложение
 Then он видит название темы, признаки, уверенность и черновик сводки
  And он видит, какие проблемы вошли в кластер (без автора и команды)

Given HR-аналитик подтвердил кластер
 When он нажимает «Подтвердить»
 Then создается запись в реестре проблем
  And назначается владелец процесса
  And действие фиксируется в model_review_log

Given HR-аналитик отклонил кластер
 When он нажимает «Отклонить»
 Then он обязан указать причину
  And проблемы остаются раздельными
  And модель не обучается на этом отказе

Given внешняя модель недоступна
 When HR-аналитик открывает очередь
 Then он видит статус «Ручной режим»
  And может классифицировать проблемы по справочнику тем
  And в model_review_log фиксируется gateway_unavailable

Given HR-аналитик не ответил за 3 рабочих дня
 When срок истекает
 Then эскалация к руководителю HR-аналитики
  And проблемы остаются в реестре в статусе «Ожидает решения»
```

### US-06. Назначение владельца и ответ

Как владелец процесса,
я хочу получить проблему с назначенным сроком и дать видимый ответ,
чтобы команда видела, что ее проблема решена или взята в работу

Критерии приемки:

```gherkin
Given кластер проблем / проблема подтвержден(а)
 When HR-аналитик назначает владельца
 Then владелец получает уведомление
  And срок подтверждения - до 10 рабочих дней

Given владелец принял кластер проблем / проблему
 When он нажимает «Принять в работу»
 Then статус меняется на «В работе»
  And команда видит это в публичном трекере

Given владелец не может принять проблему
 When он нажимает «Переназначить»
 Then он обязан указать причину и нового владельца
  And действие фиксируется в action_log

Given владелец не ответил за 10 рабочих дней
 When срок истекает
 Then автоматическая эскалация к HR-директору
  And кластер проблем / проблема помечается как «Просрочено»
  And команда видит статус «Просрочено» в трекере
```

### US-07. Замыкание обратной связи

Как команда,
я хочу видеть статус своей проблемы и возможность переоткрыть ее,
чтобы доверие к процессу росло, а не падало после первого же цикла

Критерии приемки:

```gherkin
Given проблема находится в работе
 When владелец обновляет статус
 Then команда видит изменение в публичном трекере
  And не видит внутреннюю переписку и детали других команд

Given владелец отметил проблему как «Решена»
 When команда открывает карточку
 Then она видит описание изменений
  And может анонимно проголосовать «Согласны» или «Не согласны»

Given команда не согласна с закрытием
 When голосование завершено
 Then проблема переоткрывается
  And в closure_log фиксируется reopened и причина
  And владелец обязан ответить в новый срок

Given владелец не обновил статус за 30 дней
 When срок истекает
 Then автоматическая эскалация к владельцу уровнем выше
  And команда видит статус «Просрочено»
```

### US-08. Управление политикой внешней модели

Как специалист по приватности,
я хочу включать и отключать внешнюю модель,
чтобы контролировать, что и куда уходит, и иметь возможность остановить процесс

Критерии приемки:

```gherkin
Given специалист по приватности открыл панель политики AI Gateway
 When он включает режим «Внешняя модель»
 Then он видит список категорий проблем и вендора
  And должен подтвердить, что вендор поддерживает zero-retention

Given специалист по приватности отключил внешнюю модель для категории
 When проблема этой категории поступает в AI Gateway
 Then вызов не выполняется
  And классификация проблемы уходит в ручной режим
  And в gateway_policy_log фиксируется disabled и причина

Given DLP нашел ПДн на выходе
 When вызов заблокирован
 Then проблема возвращается на обезличивание
  And в dlp_outbound_log фиксируется инцидент
  And специалист по приватности получает уведомление

Given специалист по приватности не ответил за 2 рабочих дня
 When срок истекает
 Then действует предыдущая политика
  And инцидент эскалируется к HR-директору
```

## Use Cases

### UC-01. Полный цикл чек-апа от старта до замыкания

| Поле | Значение |
|---|---|
| Актеры | HR-аналитик, сотрудник, команда, фасилитатор, специалист по приватности, владелец процесса. HR-директор - только в альтернативных сценариях эскалации |
| Предусловия | Команда ≥ 5 человек, цикл создан, правило приватности зафиксировано, вендор внешней модели подтвердил zero-retention |
| Триггер | HR запускает новый цикл чек-апа |

Основной сценарий:
1. HR создает цикл: параметры, сроки, правило приватности.
2. Сервис идентификации выдает сотрудникам одноразовые токены.
3. Сотрудники приватно ставят оценки и выбирают теги.
4. Детерминированный агрегатор проверяет порог ≥ 5 и считает распределения.
5. Команда проводит сессию с фасилитатором, обсуждает разногласия.
6. Команда формулирует системную проблему.
7. Команда анонимно голосует, кворум ≥ 70%, поддержка ≥ 60%+.
8. Специалист по приватности проверяет риск идентификации.
9. Проблема регистрируется в реестре, проходит обезличивание.
10. AI Gateway проверяет политику и DLP, вызывает внешнюю модель.
11. HR-аналитик подтверждает кластер проблем / проблему, назначает владельца.
12. Владелец принимает кластер проблем / проблему, обновляет статус.
13. Команда видит статус, при необходимости переоткрывает проблему.
14. Следующий цикл: проверка динамики доверия.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 7a | Кворум < 70% или поддержка < 60% | Проблема не передается, фиксируется в consent_log, команда может переформулировать |
| 8a | Специалист по приватности нашел риск | Специалист по приватности запрещает публикацию или возвращает на правку, проблема не регистрируется |
| 10a | Внешняя модель недоступна | AI Gateway возвращает ошибку, HR-аналитик переходит в ручной режим, проблема не теряется |
| 10b | Специалист по приватности отключил внешнюю модель для категории | Вызов блокируется, проблема обрабатывается вручную |
| 11a | HR-аналитик отклонил предлагаемый кластер | Проблемы остаются раздельными, фиксируется причина в model_review_log |
| 12a | Владелец не может принять проблему | Переназначение с объяснением и новым маршрутом |
| 13a | Команда не согласна с закрытием проблемы | Проблема переоткрывается, владелец обязан ответить в новый срок |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 3a | Сотрудник использует токен повторно | Вход отклоняется, попытка фиксируется в журнале |
| 3b | Сотрудник не завершил форму | Запись не сохраняется, TTL не создается |
| 4a | В команде < 5 ответивших | Срез не публикуется, предлагается когортный отчет или офлайн-сессия |
| 10c | DLP нашел ПДн на выходе | Вызов блокируется, проблема возвращается на обезличивание |

Постусловия: проблема имеет владельца, срок и видимый статус, в журнале аудита зафиксированы все действия, команда видит результат цикла.

### UC-02. Обработка отказа команды от передачи проблемы

| Поле | Значение |
|---|---|
| Актеры | Команда, фасилитатор, HR |
| Предусловия | Проблема сформулирована, голосование запущено |
| Триггер | Кворум < 70% или поддержка < 60% |

Основной сценарий:

1. Фасилитатор запускает анонимное голосование.
2. Система показывает только кворум и долю поддержки.
3. Голосование не проходит порог.
4. Проблема помечается как «Не одобрена».
5. Запись фиксируется в consent_log с агрегатом голосования.
6. Команда обсуждает, можно ли переформулировать проблему.
7. Если команда решает оставить проблему внутри - цикл закрывается локально.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 6a | Команда решила переформулировать проблему | Возврат к шагу формулировки, новое голосование |
| 6b | Проблема затрагивает угрозы жизни, домогательства или коррупцию | Маршрут в отдельный защищенный канал, минуя голосование |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 1a | Фасилитатор пытается опубликовать проблему вместо команды | Система блокирует действие, инцидент фиксируется |

Постусловия: проблема не покинула команду, в consent_log есть запись, команда сохраняет контроль над проблемой.

### UC-03. Обработка недоступности внешней модели

| Поле | Значение |
|---|---|
| Актеры | HR-аналитик |
| Предусловия | Проблема согласована командой и обезличена, политика безопасности разрешает вызов |
| Триггер | Внешний API возвращает ошибку или таймаут |

Основной сценарий:

1. AI Gateway пытается вызвать внешнюю модель.
2. API возвращает ошибку или не отвечает в SLA.
3. AI Gateway фиксирует инцидент в журнале вызовов.
4. HR-аналитик получает уведомление о необходимости кластеризации в ручном режиме.
5. Проблема остается в очереди со статусом «Ручная кластеризация».
6. HR-аналитик кластеризует проблемы по справочнику тем.
7. В model_review_log фиксируется gateway_unavailable и ручное решение.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 2a | API восстановился до ручной обработки | AI Gateway выполняет отложенный вызов, проблема возвращается в автоматический поток |
| 6a | Объем проблем слишком велик для ручной обработки | HR-аналитик приоритизирует проблемы по частоте тегов, остальные остаются в очереди |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 1a | Специалист по приватности отключил политику вызова | Вызов не выполняется, проблема сразу уходит в ручной режим |
| 7a | Внешняя модель вернула некорректный ответ | HR-аналитик отклоняет предложенный кластер с причиной |

Постусловия: проблема не потеряна, кластеризация выполнена человеком, инцидент зафиксирован, архитектура не изменилась.

## Нефункциональные требования

| Категория | Требование | Проверяемость |
|---|---|---|
| Производительность | Время отклика AI Gateway ≤ 5 секунд на один вызов, очередь не теряет проблемы при пиковой нагрузке (до 500 проблем в сутки) | Нагрузочный тест, мониторинг длины очереди |
| Надежность | Процесс не останавливается при недоступности внешней модели, ручной режим сохраняет работоспособность | Учения по отказу API, проверка fallback на ручную кластеризацию |
| Безопасность | Доступ по ролям (RBAC), шифрование данных в покое и при передаче, MFA для IAM и панели специалиста по приватности | Пентест, аудит ролей, проверка шифрования |
| Приватность | TTL 24 часа на индивидуальные ответы, k ≥ 5 для любого среза, отсутствие ПДн на выходе в AI Gateway | Автотесты на удаление, DLP-тесты, проверка k-анонимности |
| Объяснимость | Каждое предложение модели содержит признаки, уверенность и источники, каждое решение человека фиксируется с причиной | Аудит выборки решений |
| Аудит | input_hash для каждой обезличенной проблемы, gateway_version и model_version в журнале | Аудит логов, проверка восстановимости решения по хешу |
| Локализация | Интерфейс и уведомления на русском языке, данные обрабатываются в РФ (152-ФЗ), при передаче за рубеж - уведомление и оценка по GDPR/SCC | Юридическая экспертиза, проверка маршрутов данных |
| Сопровождаемость | Все параметры процесса вынесены в конфигурацию и версионируются без изменения кода: правила приватности, порог k, кворум и поддержка, сроки SLA, справочник тегов, роли доступа. AI Gateway, компонент «Защита конфиденциальности», агрегатор и сервис идентификации заменяемы через абстракции. Отключение ИИ переводит процесс в ручной режим без потери данных | Изменение порога k или кворума не требует релиза кода - только обновление конфигурации с записью версии, тестовая замена вендора ИИ через шлюз без изменения остальных компонентов, отключение ИИ - процесс продолжается в ручном режиме |

## Ограничения и допущения

| Ограничение | Источник |
|---|---|
| Внешний API обрабатывает данные за пределами организации | Архитектура TO-BE |
| Абсолютная анонимность в малой команде технически недостижима | Ограничение предметной области |
| Squad Health Check не используется для расследования и оценки людей | Политика процесса |
| Не разрабатываем собственную IT-платформу для опросов | Границы решения из 01_problem |
| Не используем данные обратной связи для Performance Review | Границы решения из 01_problem |

Допущения - проверяемы, подтверждение меняет архитектуру.

| Допущение | Кто подтвердит | Что меняется, если неверно |
|---|---|---|
| Вендор внешней модели поддерживает zero-retention и opt-out из обучения | Специалист по приватности | Внешняя модель не подключается, пилот стартует в ручном режиме |
| Команды готовы участвовать, если им объяснить ограничения | HR-аналитик | Потребуется дополнительная работа с доверием |
| Нейтральный фасилитатор снижает страх репрессий | Пилот на 3–5 командах | Потребуется пересмотр роли фасилитатора или дополнительная работа с руководителями |
| Кворум 70% и поддержка 60%+ достижимы в малых командах | Пилот на 3–5 командах | Порог может быть снижен |
| Сотрудники готовы говорить правду, если уверены в безопасности и видят изменения | Пилот на 3–5 командах | Придется искать другие барьеры (культурные, управленческие) |
| Передача наверх только системных проблем сохраняет actionable-ценность | Анализ качества проблем | Потребуется уточнение формата передачи |

## Definition of Ready

- [x] Пользователь и его роль определены (сотрудник, команда, фасилитатор, HR-аналитик, специалист по приватности, владелец процесса)
- [x] Ценность описана в одну фразу (достоверные проблемы без реестра индивидуальных мнений)
- [x] Критерии приемки сформулированы и проверяемы
- [x] Зависимости от других историй перечислены (US-03 → US-04 → US-05 → US-06 → US-07)
- [x] Уровень автоматизации выбран и согласован с TO-BE
- [x] Понятно, где история создает риск для человека (H1 - давление на команду, H2 - идентификация, H3 - ошибочный кластер, H4 - бездействие, H5 - незакрытый контур, H6 - утечка во внешний API)

## Definition of Done

- [x] Реализация проходит все критерии приемки
- [x] Для L1 и выше существует лог решения с объяснением (consent_log, privacy_review_log, model_review_log, action_log, closure_log, gateway_policy_log)
- [x] Есть тест на граничные и ошибочные сценарии
- [x] Права доступа настроены по ролям
- [x] Документация для пользователя обновлена
- [x] История просмотрена другим членом команды
- [x] Риски ИИ для этой истории перепроверены, контрмеры работают
